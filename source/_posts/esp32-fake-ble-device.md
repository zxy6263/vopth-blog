十几块钱买了一块 ESP32 开发板，本来只是想玩玩硬件。

结果一路玩到了"让手机相信它是另一个设备"。

一个成了，一个没成。而**没成的那个，比成了的更有意思** —— 它划出了蓝牙世界里一条清清楚楚的界线。

> 说明在前：下面所有实验对象都是**我自己的设备**（我的手机、我自己买的板子和手表）。
> 整个过程没有影响任何人，没成的那个实验也正因为做不到而停下。

<!-- more -->

## 一、这块板子

| 项目 | 内容 |
| --- | --- |
| 芯片 | ESP32-WROOM-32E |
| 串口芯片 | CH340C |
| 接口 | USB-C |
| Flash | 4 MB |
| 屏幕 | **没有** |
| SD 卡 | **没有** |

买它是因为便宜、资料多、自带 WiFi 和蓝牙 —— 后两条是它的立身之本。
同一价位里，别的单片机（比如 STM32）外设更丰富、时序更精确，但**基本都不带无线**，
要联网得再挂一个模块。ESP32 把 WiFi + 蓝牙做进了芯片，这是它最不可替代的地方。

没有屏幕这件事，后面会变成一个真实的麻烦。

固件用的是 MicroPython —— 因为它能直接写 Python、传上去就运行，不用编译工具链。
这个选择也带来了一些后面会讲到的限制。

## 二、第一个实验：让手机以为它是一条心率带

蓝牙里有一类东西叫「标准服务」，是蓝牙技术联盟（SIG）公开定义的。
**心率监测**就是其中之一，任何人照着文档实现，任何 App 都能认。

需要的东西很少：

| 服务 / 特征 | UUID | 作用 |
| --- | --- | --- |
| Heart Rate Service | `0x180D` | 心率服务本体 |
| Heart Rate Measurement | `0x2A37` | 心率数据（通知） |
| Body Sensor Location | `0x2A38` | 戴在哪儿（读） |
| Heart Rate Control Point | `0x2A39` | 控制点（写） |

为了让它看起来更像一块"表"，还加了设备信息服务，把型号、厂商、固件版本都填上：

| 服务 / 特征 | UUID | 值 |
| --- | --- | --- |
| Device Information | `0x180A` |  |
| Model Number | `0x2A24` | 自己填 |
| Manufacturer Name | `0x2A29` | 自己填 |
| Battery Level | `0x2A19` | 电量百分比 |

### 心率数据包长什么样

`0x2A37` 的载荷格式也是公开的，第一个字节是标志位：

```
bit0 = 0   心率用 1 字节表示
bit1 = 1   支持"传感器接触检测"
bit2 = 1   当前检测到接触（也就是"戴着"）
bit4 = 1   后面还带 RR 间期（两次心跳的毫秒间隔）
```

所以一个带接触状态和 RR 间期的包就是 4 个字节：

```
16 47 4D 03
│  │  └─┬─┘
│  │    └─ RR 间期 = 0x034D = 845 毫秒
│  └─ 心率 = 0x47 = 71 bpm
└─ flags = 0b00010110
```

### 心率不能乱跳

第一版我用随机数生成心率，结果数字每秒乱跳 —— **假得一眼就看出来**。

真人的心率是**缓慢漂移**的。改成"随机漫走"（每次只在前一秒的值上挪一点点，
再加上轻微回归到目标值），立刻就对了：

```
心率  71 bpm   RR 845 ms
心率  71 bpm   RR 845 ms
心率  72 bpm   RR 833 ms
心率  70 bpm   RR 857 ms
```

这个细节和技术无关，但它决定了这东西"像不像"。

### 结果

手机蓝牙列表里出现了这个设备，**连上了，而且配对成功**
（设备侧日志显示 `encrypted=1 bonded=1`），心率每秒稳定推送，**连着 90 多秒没有断**。

然后我发现一个反直觉的现象：

> **手机系统蓝牙界面里，什么都看不到。**
>
> 它只负责"连接"，不负责"显示数据"。所以连接明明成功了，
> 屏幕上没有任何地方能看出心率在跳 —— 我当时以为失败了。

想看到数字，得用能读标准心率服务的 App（比如 nRF Connect 这类工具）。

**这是第一个提醒：连上了 ≠ 你能看见。**

## 三、第二个实验：让它冒充一块智能手表

心率带成功之后我有点飘了，想试试能不能让板子冒充一块真的智能手表。

手里正好有一块真的，于是做法很直接：**先把真表抄一遍**。

### 3.1 抄广播包

把板子刷成一个蓝牙扫描器，让它听周围所有的广播。真表发三种包：

```
① 主广播（可连接）
   0fff 3708 00010f000700 b49d6b395855   0201 1a
   └┬─┘ └┬─┘ └──────┬──────┘            └─┬─┘
    │    │          │                     └─ Flags
    │    │          └─ 手表自己的 MAC 反序
    │    └─ 厂商 ID
    └─ 厂商自定义数据

② 不可连接广播
   1a16 8808 0103400318776d80dcf77be6abbb773c0e1b166ee8fff1
   └─ 服务数据，UUID 0x0888

③ 扫描响应
   1309 "iQOO WATCH GT2 855"
```

**名字在第三个包里。** 这是个容易踩的坑：扫描时必须用主动模式，
否则收不到扫描响应 —— 你会看到一堆"隐藏设备"，其实人家的名字就在那儿。

### 3.2 抄服务表

让板子当主机去连真表，把它的 GATT 表整个扒下来。**六个服务、十五个特征**，
其中三个是厂商私有的（UUID 是 128 位的随机串，不是标准的那几个）。

**这一步有个意外发现：连上就能读全部服务，全程没有触发任何配对或加密。**

也就是说 —— **认证不在蓝牙层**。

### 3.3 抓手机的蓝牙包

接下来想知道 App 跟表之间到底说了什么。

安卓可以打开系统级的蓝牙抓包（开发者选项里那个"HCI 信息收集日志"），
但日志文件在 `/data/misc/bluetooth/logs/`，普通权限读不到。

绕过去的方法是走系统诊断包：

```powershell
# 1. 开抓包开关（设置会一直保留）
adb shell settings put secure bluetooth_hci_log 1

# 2. 让目标设备做一次你关心的交互（日志是滚动的，动作要新鲜）

# 3. 拉诊断包
adb bugreport D:\path\br

# 4. 从套娃压缩包里挖日志
#    br.zip → bugreport-XXXX.zip → FS/data/misc/bluetooth/logs/*.cfa
```

这里有个小插曲：挖出来的文件扩展名是 `.cfa`，我一度以为是什么私有格式。
结果看文件头 —— `btsnoop\0` —— **就是标准的 btsnoop 抓包文件**，改个名就能正常解析。

**别被扩展名骗了，看文件头。**

### 3.4 协议居然是明文的

自己写了个解析器（ACL 分片重组 → L2CAP → ATT），然后算了一件事：**字节熵**。

```
CID 0x0041   熵 4.23 bit/byte
CID 0x0042   熵 3.07
CID 0x0043   熵 3.83     ← 而且 127/563 个包有超过 60% 的可打印字符
CID 0x0044   熵 3.16
```

**加密数据的熵应该在 7.9 附近。这些都是 3~4，说明是明文。**

而且结构一眼能看出来 —— 是 TLV（标签-长度-值）：

```
06 000000 1c 35 0319 1200 02 0035 1209 0200 0902 0109 0202 0902 0309 0204 0902 0500
                                              └09 02 00┘└09 02 01┘└09 02 02┘
```

主通道上的包还有固定的同步头（某个字节出现 537 次）。

到这一步，我的判断是"**这条路能走**"。

### 3.5 然后撞墙了

墙有三层，一层比一层硬。

**第一层（技术能力）：目标用的是 L2CAP CoC，而板子上的 MicroPython 没有这个能力。**

蓝牙的数据通道不止一种。普通 GATT 走的是 ATT 通道，而厂商私有的高速数据通道
往往用 L2CAP CoC（面向连接的通道）—— 抓包里那些动态 CID 就是它。

我查了一下板子上 BLE 的全部能力：

```python
>>> print([m for m in dir(bluetooth.BLE()) if not m.startswith('_')])
['active', 'config', 'gap_advertise', 'gap_connect', 'gap_disconnect',
 'gap_pair', 'gap_passkey', 'gap_scan',
 'gattc_discover_characteristics', 'gattc_discover_descriptors',
 'gattc_discover_services', 'gattc_exchange_mtu', 'gattc_read', 'gattc_write',
 'gatts_indicate', 'gatts_notify', 'gatts_read', 'gatts_register_services',
 'gatts_set_buffer', 'gatts_write', 'irq']
```

**`l2cap_*` 一个都没有。** MicroPython 的这个功能默认编译开关是关的，
官方固件里没有。

（技术上不是死路 —— 可以自己编译一个开了开关的固件，或者直接用 ESP-IDF 写 C。
但那已经是另一个量级的工程了。）

**第二层（规模）：这不是一个协议，是一整套系统。**

我把官方 App 拉下来分析了一下规模：

```
App 里一共 24,293 个类

devices/watch/dial         3165    表盘
devices/watch/health        616
devices/watch/bind          110    ← 光是"配对"就有 110 个类
lib/ble/impl                118    ← BLE 传输层
lib/ble/api                  65
```

**光"配对"这一个环节的代码量，就超过我整个博客项目。**

**第三层（可能是死路）：配对要走云端。**

App 里有一批这样的类名：

```
lib/ble/api/BindCareApiService      ← 绑定 API
lib/ble/api/DevicesApiService       ← 设备 API
lib/ble/util/SecureUtils            ← 加密工具
```

名字里的 `ApiService` 说明配对流程要调厂商的服务器接口。
**如果手表在云端是注册过的，那光复刻蓝牙协议也没用 —— 服务器那一关过不去。**

大概率还有出厂烧进安全芯片的设备密钥，那个连逆软件都拿不到。

### 3.6 所以结论是

| | 心率带 | 智能手表 |
| --- | --- | --- |
| 协议 | 公开标准 | 厂商私有 |
| 加密 | 无 | 有握手（会话密钥） |
| 云端 | 不需要 | **可能需要** |
| 规模 | 3 个特征 | 24,293 个类 |
| 结果 | 成了 | 撞墙 |

**区别不在"难不难"，在于：标准协议谁都能实现，而厂商私有协议背后是一整套系统，
还可能有你拿不到的东西。**

## 四、这一路最贵的教训：我的尺子又坏了

写博客的时候我总结过一件事：**最难查的 bug 是"我的验证工具在骗我"**。

这次又犯了，而且犯得更彻底。

本机有一块 USB 蓝牙网卡。这一整晚，我多次用它扫描，然后得出"**板子没有在广播**"的结论：

```
PC 扫描结果：只听到旁边一个邻居设备
我的结论：板子没广播
然后：让用户拔插 USB、换口、重新刷固件……
```

**反复折腾了好几轮。**

最后是用户掏出手机一看：

```
"我手机蓝牙里能看到那台设备啊"
```

板子从头到尾都好好的。

问题在那块蓝牙网卡 —— 它一整晚都时灵时不灵，最后严重到**整屋只能听见一个设备**
（正常环境不可能这么少）。它听不见我们的板子，但能听见旁边那台。

**这就是"坏尺子"最恶劣的形态：它不是完全坏掉，而是时好时坏。
时好时坏的工具比坏掉的道具危险得多 —— 因为它偶尔能给出正确答案，你会继续相信它。**

后来的做法是：**蓝牙设备的可见性一律用手机验证，PC 侧的扫描结果只作参考。**

## 五、几个和环境有关的坑

### 1. 串口的 DTR/RTS 会复位板子

```
打开串口 → CH340 拉 DTR/RTS → 板子复位一次（这是设计如此，用于下载）
关闭串口 → 引脚回默认状态 → 可能把使能脚拉低 → 板子被按住 → 停止广播
```

**实测现象：串口开着的时候板子正常广播，一关就"空中消失"。**

解法是写个小进程**占住串口不关**，同时持续读数据。
（只占着不读也不行 —— 板子每秒打印会把缓冲区填满，`print()` 阻塞主循环。）

这个坑的后果是：**每次我用命令行调试，用户的设备就会掉线几秒。**
做到后面我们分工了：他操作，我不碰串口。

### 2. MicroPython 和 CPython 的差别

给板子的脚本不能按桌面 Python 的习惯写：

```python
bytes(addr)[::-1]         # NotImplementedError: only slices with step=1 ...
raw.decode("latin-1")     # LookupError: unknown encoding: latin-1

bytes(reversed(bytes(addr)))   # 手动倒序
b"WATCH" in raw                # 直接用字节匹配
```

**语法检查过了不代表板子上能跑。**

### 3. 供电不足会重启

WiFi 和蓝牙的突发电流会拖垮弱的 USB 口，日志里出现：

```
E BOD: Brownout detector was triggered
rst:0x3 (SW_RESET)
```

换线、换口就好了。**但如果你用电池供电，这会变成常态** ——
电池电压随电量下降，快没电时一突发就掉电复位。

### 4. 没有屏幕的真实代价

在电脑边上，串口连着，什么都看得见。

**一拔线，什么都看不见了。** 板子跑成什么样、IP 是多少、当前在做什么，全靠猜。

这是我的下一个采购清单上第一项：一块 0.96 寸的 OLED，十几块钱。
**有了它，这东西才算能"带出去用"。**

## 六、做完这两个实验之后

我对蓝牙的理解可以压缩成一句对比：

> **标准协议是公开的，身份证是私有的。**

| | 能不能伪造 |
| --- | --- |
| 广播包（名字、厂商数据） | 能，随便改 |
| 标准服务（心率、电池、键盘鼠标） | 能，照着公开文档实现 |
| 厂商私有协议 | 难，要逆向 |
| 厂商的加密握手 | 很难，密钥可能拿不到 |
| 云端绑定 | **可能根本没戏** |

前面三行是"技术问题"，后面两行是"**看得见但够不着**"。

而这次实验最实际的收获，反而是那条界线本身 ——
**知道了哪里是墙，比多做出一个能跑的东西更有用。**
